# neo-personal-bot 产品 PRD

核对日期：2026-10-06。

这是产品说明，供评审角色、边界和用户看见的结果。技术选型、开源取舍和联动契约在 [选型与技术设计方案](选型与技术设计.md)。

## 问题

一个人要的是一小撮职责清楚的队友，而不是又一个通用聊天窗口。研究员负责查清问题，工程师负责改仓库。长任务在云端继续。发送、付款、删除生产，和改一行 README，走不同的路径。

## 用户

单人操作者，自己定义团队。第一版的信任域就是这一个用户。角色名表达职责，不表达凭证隔离，也不解决互不信任的多租户。

## 产品原则

从 Grok Bot 借来的是工作方式：一个角色一件可重复的结果；长期规则写在职责里，这一次的任务写在消息里；对外动作先停下来给人看；设备只负责对话和批准，电脑在云上。

留给通用助手的能力留在通用助手里：伴侣人格、公开社交回复、把多个匿名工人合成一条答案。那些不是这个产品的工作单位。

## 第一版做什么

1. 用户维护具名角色。每个角色有职责、可接触的仓库、执行后端。
2. 用户用 `@角色` 发一句话。
3. 产品把这句话分成三类：直接回复、停在审批、写成一张任务并派给云端执行。
4. 派发之后回一张卡片：角色、状态、分支、PR、错误。

建议评审用的团队：

| 角色 | 职责 | 仓库 |
| --- | --- | --- |
| 研究员 | 把事实、推断、未核实分开。不改仓库。 | 无 |
| 工程师 | 只改绑定仓库，做完留下分支和 PR。 | 用户指定的一个仓库 |

## 第一版不做

- 通用人格、伴侣、一个「什么都管」的助手。
- 把多个角色当成不同的登录隔离。发送、付款、删除生产靠审批截断。
- 记忆产品、技能市场、群聊、日程自动化。
- 自建云电脑。执行面用现成的 neo cloud agent。
- 在这一份文档评审通过之前写运行时。

## 走查故事

**改仓库。** 用户说：`@工程师 在仓库里给 README 加上一行产品一句话，并开 PR`。

产品点名工程师，确认这是仓库改动，派到该角色绑定的仓库。完成后卡片同时有：本轮结束、分支、PR 链接、空的错误。

**对外动作。** 用户说：`@工程师 给客户发送这封邮件`。

卡片状态是待审批。云端执行不被创建。用户明确同意之前，不会自动重试。

**只问问题。** 用户说：`@研究员 我们团队有哪些人`。

研究员回复团队和职责。没有仓库改动，也不派发。研究员被要求开 PR 时，产品说明这个角色没有绑定仓库，仍然不派发。

## 消息规则

- 没有 `@`：请用户点名，并列出角色。
- `@` 对不上角色：说明没有这个角色。
- 出现这些词时停在审批，即使同一句里也写了 PR：`发出去`、`发送`、`付款`、`支付`、`购买`、`删库`、`删除生产`、`删除账号`、`删除仓库`。
- 出现仓库改动用语才派发：`加上`、`修改`、`改仓库`、`提交改动`、`PR`、`pull request`。
- 单独的「删除」不自动审批。删 README 里的一行仍可能是仓库改动。生产删除要写进上面的词表。这是第一版刻意收窄的规则。

## 用户看见的卡片

| 字段 | 用户看见的意思 |
| --- | --- |
| 角色 | 被点名的队友 |
| 状态 | 排队、执行中、本轮结束、待审批、失败。旁边可以附上云端原词 |
| 分支 | 这一轮改动所在的分支 |
| PR | 可打开的链接 |
| 错误 | 没派成或这一轮失败的原因 |

状态对应关系放在技术设计里。产品侧只要求：进行中不能画成已完成；待审批不能伴随一次云端执行。

## 成功和失败

改仓库的故事成功时，卡片同时有结束状态、分支和 PR。审批故事成功时，云端没有新的执行记录。

云端拒绝创建、执行失败、或超时仍在跑，卡片保持失败或进行中，并写出原因。超时不能改写成已完成。
