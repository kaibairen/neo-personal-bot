# neo-personal-bot 产品 PRD

核对日期：2026-10-06。仓库起点只有一句说明：「个人化的可自定义工作团队」。

## 问题

一个人要的不是又一个通用聊天窗口，而是一小撮职责清楚的队友：研究员负责查清问题，工程师负责改仓库。长任务不该占着笔记本，也不该把「发送、付款、删除」和「改一行 README」走成同一条自动路径。

Grok Bot 已经把「命名队友 + 云端电脑 + 消息即界面」做成了成品。neo-personal-bot 借鉴这层，不复刻 grok.com 的通用助手，也不把公开社交回复当成工作单位。

## 用户

单人操作者，自己定义团队。第一版不解决互不信任的多租户。角色都在这一个用户的信任域里，角色名不是安全边界。

## 做什么

1. 用户维护具名角色。每个角色有职责、可接触的仓库、执行后端。
2. 用户用 `@角色` 发一句话。
3. 控制面分类：直接回复、停在审批，或写成一张内部任务票。
4. 任务票派给 neo cloud agent。回一张卡片：角色、状态、分支、PR、错误。
5. 同一条故事可以在命令行和网页上展出，不接真云也能看完。

展出团队固定为两个角色：

| 角色 | 职责 | 仓库 |
| --- | --- | --- |
| 研究员 | 把事实、推断、未核实分开。不改仓库。 | 无 |
| 工程师 | 只改绑定仓库，做完留下分支和 PR。 | `https://github.com/kaibairen/neo-personal-bot` |

## 不做什么

- 不做通用人格，不做伴侣，不做一个「什么都管」的助手。
- 不在控制面里跑 shell、克隆仓库或持有模型供应商密钥。
- 不把 Neo 的 `POST /v1/runs` 和 Cursor 的 `POST /v1/agents` 收成同一个请求体。
- 不把同一用户的多个角色当成凭证隔离。发送、付款、删除生产靠审批截断，不靠角色名。
- 第一版不做记忆产品（Mem0、Letta、Graphiti）、不做技能市场、不做群聊、不做日程 routine。
- 不 fork OpenClaw、Paperclip、Dify、FastGPT 或 Coze Studio。

## 故事

**成功。** 用户说：`@工程师 在 neo-personal-bot 里给 README 加上一行产品一句话，并开 PR`。

控制面点名工程师，确认这句话要改仓库，写成任务票：职责在指令里，仓库在 `repoUrls`，模式是 `agent`。适配器 `POST /v1/runs`。轮询到 `IDLE` 后，卡片给出 `neo/readme-line` 和 PR 链接。展出环境用录像代替真云，字段和真接口一致。

**审批。** 用户说：`@工程师 给客户发送这封邮件`。

命中「发送」。卡片状态是待审批。适配器的创建方法不被调用。同意之前不会静默重试。

**不派发。** 用户说：`@研究员 我们团队有哪些人`。

研究员没有仓库改动要做，只回复职责和团队。`@研究员 …开 PR` 会失败并说明该角色没有仓库，仍然不派发。

## 消息规则

- 没有 `@`：请用户点名，并列出角色。
- `@` 对不上角色：说明没有这个角色。
- 下面这些词出现时停在审批，即使同一句里也写了 PR：`发出去`、`发送`、`付款`、`支付`、`购买`、`删库`、`删除生产`、`删除账号`、`删除仓库`。
- 出现仓库改动用语（`加上`、`修改`、`改仓库`、`提交改动`、`PR`、`pull request`）才派发。
- 单独的「删除」不自动审批。删 README 里的一行仍可能是仓库改动。这是第一版的缺口，不是一条隐蔽的生产删除通道；生产删除要写进上面的词表。

## 卡片

| 字段 | 含义 |
| --- | --- |
| 角色 | 被点名的队友 |
| 状态 | 内部状态，并附上云端原词，例如 `本轮结束（IDLE）`、`待审批` |
| 分支 | Neo 的 `branchName`，或 Cursor run 的 `git.branches[].branch` |
| PR | Neo 的 `pullRequests[].url`，或 Cursor 的 `prUrl` |
| 错误 | 云端 `errorMessage`、run 失败原因，或 HTTP 拒绝原因 |

Neo 的 `NOT_YET_STARTED` 显示为排队。`PROVISIONING`、`INSTALLING`、`RUNNING`、`WAITING_FOR_BACKGROUND_WORK` 显示为执行中，不算成功。`ERROR` 是失败。`ARCHIVED` 和 `EXPIRED` 是结束，但不是交付。

Cursor 看 run，不看 agent。agent 可以是 `IDLE`，同时 run 是 `ERROR`。

## 成功时用户看到什么

工程师那条样例的卡片同时有：状态 `IDLE`、分支、PR、空的错误。审批样例的派发次数不增加。

## 失败时用户看到什么

- 云端 `400`：卡片为未派发，错误用对方的 `error` 字符串，例如 `prompt is required`。不继续轮询。
- 云端 run `ERROR`：卡片为失败，并带上错误说明。
- 轮询次数用尽仍在执行：卡片保持进行中的原状态，不把它画成已完成。
